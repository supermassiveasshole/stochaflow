# 普通脚本不够用以后，再考虑通用工作流编排器

> 文档类型：功能计划
>
> 工作状态：暂停（Parked）
>
> 当前可用性：现在可用 Python 或 shell 顺序调用独立操作；通用编排器尚未实现。

当前的 `train`、`sample` 和 `evaluate` 都是可以独立运行的操作。用户若只想按顺序完成两三
件事，用普通 Python 或 shell 脚本调用它们，并把 checkpoint 或结果目录显式交给下一步，就
已经足够。几行顺序调用容易阅读、容易调试，也不需要学习另一套工作流概念。

因此，仓库现在没有通用的步骤清单、跨步骤状态文件或失败恢复器。这不是一个急着填补的
缺口。通用编排器只有在多条长期维护的工作流开始重复同一套状态、重试和恢复代码时，才会
比普通脚本更简单。

## 两条真实工作流会先于编排器出现

第一条可能的工作流是“训练教师，再蒸馏学生”。用户先训练教师模型并得到正式 checkpoint，
再把这个结果交给学生蒸馏训练，最后用独立 Evaluation 检查学生 checkpoint。这里真正重要的
不是把三条命令包在一起，而是第二步能够确认拿到的确实是第一步发布的教师结果，第三步也能
确认评估的是本次产生的学生结果。

第二条可能的工作流是“先生图，再做超分辨率”。采样先发布一份完整的图片文件包，超分操作
读取这份文件包并发布高清结果，Evaluation 再给出正式质量结果。中途传递的不是一个碰巧存在
的裸路径，而是能够验证来源和完整性的运行产物。

这两条工作流目前都由各自的产品计划负责。近期如果选择其中一条，只会先把独立操作顺序接
起来，具体方向见[内置操作与工作流组合](default-workflow-pipeline-support-plan.md)。本计划不会
抢在真实工作流之前设计一套通用语法。

## 普通脚本什么时候才真的不够

一条工作流稳定运行后，维护者可以观察它的脚本是否开始反复处理这些事情：

- 给每一步分配不会变化的名称；
- 保存这一步读了什么、正式发布了什么；
- 再次运行时判断一个旧结果能否安全复用；
- 记录失败位置，并从失败处继续；
- 取消运行、清理中间文件，又不破坏已经发布的结果。

单条工作流出现这些代码仍然不足以抽象。至少两条独立、已维护的工作流要重复同一种生命
周期，且维护者能够指出删除了哪些重复代码，通用编排器才有启动证据。如果两条流程看似
相似，实际却用不同方式判断完成或恢复，就继续保留各自的普通脚本。

## 真正需要时，第一版只解决顺序执行

有了重复证据后，第一版也只接受一组按顺序运行的现有操作。用户提供每一步的完整配置，并
明确说明它读取上一步的哪份正式结果；框架记录每一步尚未开始、正在运行、已经完成或失败，
在进入下一步前验证输入确实属于本次工作流。

用户应能查看当前进度、取消尚未完成的工作，并在修复配置或外部问题后只重试失败步骤。
已经发布且身份匹配的结果不会被悄悄重算，身份不匹配的旧结果也不能冒充本次输出。进程中断
后，恢复逻辑从状态记录和正式产物重新判断，而不是仅凭某个目录存在就跳过工作。

第一版不会支持分支、循环、运行时改变结构的任意流程图，也不会负责远程集群的队列、机器
分配或自动扩缩容。Airflow、Kedro、ZenML 等外部系统已经处理更大的调度问题；Stochaflow
只在确有重复时负责自己现有操作之间的结果交接和恢复语义。

## 什么证据表示它已经做对

完成时，至少两条维护中的真实工作流要在不修改通用运行器的情况下，共用同一套顺序执行、
状态记录和失败恢复代码。中断、重试、取消、结果身份不匹配和部分发布都要有失败测试；同时
直接运行单个 `train`、`sample` 或 `evaluate` 仍然简单，不需要先创建工作流。

编排器不会实现任务自己的训练、采样、超分或 Evaluation 算法，也不会自动猜测哪些操作应该
相连。把未实现的操作写进步骤列表，不能让那个操作变成可用功能。
