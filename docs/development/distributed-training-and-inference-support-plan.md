# 多设备训练与采样计划

> 文档类型：功能计划
>
> 工作状态：暂停（Parked）
>
> 当前可用性：训练、采样和 Evaluation 现在都只支持一个进程，不能把同一次运行分给多个设备。

## 多一个设备，不只是多一份模型

多设备支持只在一个已经正确的单设备任务遇到明确限制时有价值：要么一个设备装不下需要的
batch，要么完成一次已验证任务的时间超过预算。首版会使用 DDP（分布式数据并行）：每个设备
运行一个进程、保存一份完整模型、读取不同样本，再同步模型更新。

看起来只要给模型包一层 DDP 就够了，实际并不是。四个进程还要知道谁读取哪些数据，怎样把
四份局部指标合成一份全局结果，谁保存训练进度，以及任一进程失败时怎样让整次运行一起失败。
采样时，它们还要生成互不重复的样本，并最终发布成一个普通结果，而不是留下四个互不相干的
目录。只有这些问题一起解决，多设备运行才仍然是“一次训练”或“一次采样”。

仓库现有的单设备训练、checkpoint、原子发布、全局样本编号和独立采样流程可以成为基础。
但当前没有进程启动、数据分工、全局指标、共同保存状态、跨进程失败处理或结果合并，所以这项
功能现在不能使用。

## 用户启动多个进程，最后仍只看到一场训练

PyTorch 的 `torchrun` 可以启动多个 Python 进程。未来用户会给它一份已经能单设备训练的普通
YAML，再选择固定数量的进程和 DDP。下面只说明预期体验：**Stochaflow 的入口、参数和配置
字段当前都不存在，不是公共 API，命令不能执行。**

```text
torchrun --nproc-per-node=4 \
  <未来的 Stochaflow 多设备训练入口> \
  --config configs/train/afhq.yaml \
  --distributed ddp
```

四个进程读取不同训练样本、同步更新，并把局部统计合成同一份 validation 结果。成功以后，
用户看到的是一套共同结果：

```text
outputs/.../<run-id>/
├── resolved_config.yaml
├── run_manifest.yaml                 # 整次运行的状态和来源
├── <分布式训练状态目录>/              # 用相同进程数继续中断的训练
└── checkpoints/
    └── best.pt                       # 普通采样和 Evaluation 可读取
```

尖括号中的名称还没有确定。首版只保证从完整 epoch 边界继续训练，并要求使用相同的进程布局；
不会承诺从一个 batch 或 epoch 中间恢复。

这里必须把两种保存结果分开。分布式训练状态包含继续训练需要的模型、optimizer、学习率调整器、
混合精度状态、EMA、训练进度和各进程随机数状态，缺少任何分片都不能恢复。另一方面，还要导出
一份完整推理 checkpoint，让普通采样与 Evaluation 无需知道训练曾经用了几个进程。训练状态
目录不能伪装成普通模型文件。

## 多设备采样也要发布成一份完整结果

未来的多进程采样仍由 `torchrun` 启动。下面同样只是**不可执行、非公共 API 的体验说明**：

```text
torchrun --nproc-per-node=4 \
  <未来的 Stochaflow 多设备采样入口> \
  --checkpoint outputs/.../checkpoints/best.pt \
  --config configs/sample/afhq.yaml
```

采样请求会按稳定的全局样本编号分给各进程。每个进程只把自己的结果写入临时目录；全部成功
后，主进程检查缺失和重复，再发布一个普通采样目录及其结果清单。图片和大 tensor 不应为了
合并而集中复制到主进程内存。某种输出如果只能写成单文件，具体输出组件必须自己提供明确的
合并方法。改变进程数不能改变样本身份，用户也不需要手工拼接结果。

## 数据分工必须在读取数据之前说清楚

多进程运行中，一个进程的编号叫 `rank`，参加运行的进程总数叫 `world size`。任务的数据组装
代码 `DataBuilder` 在创建 DataLoader 时就要拿到这些信息，明确每个样本怎样分配、是否丢弃或
补齐，以及 validation 能否做到无遗漏、无重复。框架不能在事后猜测并替换任意 DataLoader
的 sampler。

所有训练进程还必须以相同次数和顺序参加同步。某个进程提前读完数据、跳过更新或出现无效
loss 时，不能让其余进程继续假装正常；所有进程要共同决定是否继续。进程看到的配置必须一致，
任一进程异常、超时或被用户中断时，整次运行一起失败并清理进程组，不能发布看似成功的清单。

## 全局训练决定不能来自四个局部平均数的平均

各进程读取的样本数可能不同，所以简单平均它们各自的 loss 平均值会得到错误答案。实现要合并
总和与计数，或合并指标自己声明的统计数据。best checkpoint、early stopping 和学习率调整
只能依据同一份全局 validation 结果，所有进程必须作出同一决定。

通用训练代码负责接入 DDP，任务训练代码仍通过现有公开接口使用模型。内置任务和外部扩展
必须走同一条路径，不能按任务名称、模型名称或具体类增加特殊分支。

## 先证明单机 DDP 确实必要

多进程会显著增加故障排查、文件保存和平台测试成本，所以本计划保持暂停。开始前必须先有一项
通过正式 Evaluation 的真实任务，以及可重复的单设备测量。测量还要证明减小 batch、混合精度、
编译或用重算中间结果节省显存（activation checkpointing）等较简单办法仍不能满足容量或时间
要求。

届时要明确硬件、操作系统、设备数量和进程通信方式（PyTorch 称为 backend），并按当时
`uv.lock` 的依赖版本实际测试 DDP、进程启动和分布式 checkpoint。验收环境至少包括能进入 CI
的 CPU 多进程测试，以及真实 CUDA 环境。满足这些条件只允许开始单机、固定设备数量的 DDP
训练和多进程采样，不会顺带批准其他并行方式。

## 第一版刻意停在完整模型能放进单个设备的地方

首版不会实现 FSDP2。只有模型状态本身放不进一个设备时，才研究怎样把模型参数、optimizer
和 EMA 分片。多节点与弹性运行也要等单机仍不满足目标、并且有真实网络环境可以验收时再做。

以下想法继续保留，但每一项都需要单独的任务、测量和完成标准：改变进程数后继续训练、恢复
epoch 中途的数据位置、精确的分布式 Evaluation、张量并行、流水线并行、三维并行、DeepSpeed、
Megatron、ZeRO 等适配，以及按全局 batch 自动调整学习率。完成 DDP 不表示这些能力已经可用。

## 一场多设备运行怎样才算真的只有一份结果

实现完成时，单进程模式必须与当前配置、结果和文件格式保持一致。单进程与 DDP 运行同一个
小型任务时，样本覆盖、全局指标、模型更新次数、best checkpoint 和停止决定应符合明确的
等价规则。使用相同进程布局继续训练时，后续状态也必须符合文档保证。

故障测试要覆盖中断、超时、单个进程崩溃、状态分片缺失和发布失败，确认它们不会留下伪造的
成功结果。分布式训练状态与完整推理 checkpoint 要有不同名称、格式、读取方式和用途。多进程
采样必须无缺失、无重复，并且只发布一份完整结果。用户文档只能列出真正验收过的平台、设备
和通信方式，未验证组合会被拒绝。

平台调研、数据分片规则、全局指标算法、checkpoint 事务、FSDP2、多节点、弹性运行和其他并行
方式保存在

这些草案不是当前接口，开始实施时必须按目标硬件和当时的 PyTorch 版本重新验证。
