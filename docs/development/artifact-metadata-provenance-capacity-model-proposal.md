# 运行产物以后还可能需要回答的三个独立问题

> 文档类型：研究备忘
>
> 排期状态：不参与排期
>
> 当前可用性：各种运行产物已经能自证身份和完整性，但没有跨任务的统一查询功能。

这里的**运行产物（artifact）**，是一次正式命令保存的 checkpoint、预测文件、结果目录，
以及用来核对这些文件的结果清单（manifest）。现有产物已经保存了恢复、读取和验证自身所需
的信息；用户现在可以训练、采样和评估，不需要等待本提案。

随着工作流变长，用户可能会对这些文件提出三个不同的问题：这份文件是什么、它是怎样
产生的、这次工作大约用了多少资源。三个问题看起来都与“产物信息”有关，但写入者、读取者
和正确性要求并不相同。因此本文保存三个独立构想，而不是把它们伪装成一个等待实施的大
项目。它们应分别按自己的证据决定是否实施；任何一个构想只有出现真实写入方、读取方和
用户操作后，才会单独进入路线图。

## 想看懂一份文件里装了什么

第一个故事很简单：用户拿到一个 checkpoint、数据产物或结果目录，想知道它对应什么任务、
使用什么图像尺寸、类别集合、数据版本或 codec，以及数据应怎样引用、许可证是否允许继续
使用。这些是给人看的说明，能够帮助用户判断文件是否适合下一步工作。

现在，每个任务已经可以把自己的说明写进结果清单，但框架没有一个跨任务的公共查看入口。
这不构成当前功能缺口。单个任务需要的字段继续留在该任务自己的格式里；只有至少两个独立
任务写入同一种事实，而且至少两个真实功能按同一种含义读取它时，才值得设计公共字段和
只读查看入口。

给人看的标签不能代替用于恢复和校验文件的固定身份。说明与内容摘要或 checkpoint 已经固定
的事实冲突时，读取必须失败，不能让一段更好看的文字覆盖真实内容。

## 想追查一个结果经过了哪些步骤

第二个故事来自多步工作流。用户看到一组高清图片，想一路追问：超分辨率使用了哪组低清
图片和哪个 checkpoint，低清图片又由哪次采样生成，生成模型使用什么训练数据、完整配置和
随机种子。这样的追查可以帮助复现实验，也可以解释两个看似相同的结果为什么不同。

当前每种产物已经记录维持自身正确性所需的来源，但 checkpoint、预测文件和结果目录之间
没有统一的来源查询。只有真实用户流程必须跨两种以上产物追查关系时，才应选择一种最小的
公共关系来实现，而不是先建一张能够描述所有实验的图。

正式命令产生的事实应由负责运行该命令的代码写入。普通 Python 代码如果也要进入同一条
来源链，必须先有明确的一次运行记录；框架不能检查调用栈后猜测发生了什么。未来可能需要的
事实还包括转换顺序、代码版本、最终配置和运行环境，但它们目前都不是公共字段。

## 想在运行前后知道资源够不够

第三个故事发生在昂贵任务上。开始前，用户想知道大约需要多少磁盘、内存、显存或计算时间，
以免运行到一半失败；结束后，用户又想知道实际用了多少，方便安排下一次任务。

“最终文件占了多少空间”“按配置估计可能需要多少资源”和“运行时真正观察到多少资源”是
三种不同事实。预计值必须与实测值分开，硬件、软件版本和测量方法也必须写清楚。当前没有
通用估算器或调度器；单个任务可以在自己的文档或结果中记录实测数字，但不能把猜测包装成
框架保证。

只有一个真实工作流需要在启动前根据资源信息作决定，或者多个运行器确实读取同一种实测
记录时，才选择其中一项做成产品能力。其余资源想法继续留在研究材料中。

## 三个构想共同遵守的边界

checkpoint、数据产物、预测文件和 Evaluation 结果已经有各自的身份与校验规则。正式命令会
保存最终配置、输入来源和输出位置，发布时不会把半成品当成成功结果，读取时也会检查文件
摘要、数量和完整性。这些现有能力不能被一个跨任务查询层替代或削弱。

未来无论选择哪个构想，都不会建立组织级数据目录、搜索服务或信息仓库，不会把任意 Python
对象或服务商私有字段塞进稳定文件格式，也不会建立通用资源调度器。保存这份提案不表示三项
功能已经排期，更不要求它们一起实施。
