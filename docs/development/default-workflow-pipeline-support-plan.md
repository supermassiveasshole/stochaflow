# 把独立操作顺序接起来：内置工作流计划

> 文档类型：功能计划
>
> 工作状态：候选（Candidate）
>
> 当前可用性：`train`、`sample` 和 `evaluate` 可以分别运行，但仓库还不能把它们可靠地接成“训练后蒸馏”或“生图后超分”工作流。

## 两个很自然、现在却很费事的使用故事

第一个故事是训练教师模型，再用教师训练一个更快的学生模型。用户真正想表达的是：先完成
教师训练，确认教师结果完整，再把这份结果交给蒸馏训练；学生训练完成后，用学生任务自己的
Evaluation 配置做正式评估。

```text
教师训练数据和配置
  -> 教师 checkpoint 和训练结果
  -> 带版本的教师文件包
  -> 学生 checkpoint
  -> 不可修改的 Evaluation 结果包
```

教师文件包不能只是一条权重路径。它还要说明教师怎样输出预测、采用什么导出版本，以及文件
是否完整。蒸馏算法仍由具体任务负责；顺序工作流只负责把经过检查的教师结果交到它手里。

第二个故事是先生成图片，再把这些图片放大。用户先用一个生成模型运行 `sample`，然后把完整
发布的图片交给独立的超分辨率操作，最后按超分任务的规则评估高分辨率结果。

```text
生成模型 checkpoint 和采样配置
  -> 完整的采样结果
  -> 独立的超分配置和高分辨率图片
  -> 不可修改的 Evaluation 结果包
```

这两条流程都是明确保留的未来功能。第一次实现只会选择其中一条跑通，另一条不会因此被取消。

## 真正的问题不是调用顺序，而是结果怎样交接

今天，用户可以自己写脚本依次执行几个命令，但脚本往往只能拿到一个目录，再靠文件名和扩展名
猜测里面哪个 checkpoint 或哪批图片可用。目录可能只写了一半，checkpoint 可能选错 raw/EMA
权重，图片也可能缺失或重复。下一步如果直接读取这种裸路径，错误通常要到计算开始后才暴露。

所以工作流不能只是“依次运行几条命令”。每一步必须先完成自己的原子发布，再返回一份小而
明确的结果：它是什么、保存在哪里、是否完整、包含多少样本；checkpoint 还要写清下游应使用
刚训练出的原始权重（raw），还是训练中平滑保存的权重（EMA）。下一步只接收自己声明支持的
结果类型，并在开始计算前核对文件、完整性和权重选择。

失败边界也因此变得清楚。某一步失败时，工作流停止，但已经完整发布的上游结果不被改写。
用户修正配置后只重跑失败的一步，不必重新计算教师或重新生成已经合格的图片。

## 用户最终写的仍是普通 Python

下面只用来说明结果交接的体验。**这些函数当前不存在，名称和参数也不是公共 API，代码不能
执行。**

```python
# 训练教师，再蒸馏学生。
teacher = train("teacher.yaml")
teacher_files = export_teacher(teacher.checkpoint)
student = train("distill.yaml", teacher=teacher_files)
report = evaluate("student-evaluation.yaml", checkpoint=student.checkpoint)

# 生成图片，再做超分辨率。
images = sample("generate.yaml", checkpoint="generator.ckpt")
high_resolution = upscale("x4.yaml", images=images.files)
report = evaluate("sr-evaluation.yaml", predictions=high_resolution.files)
```

每个调用仍有自己的配置、输出目录、返回结果和报错范围。工作流不会把训练、采样和 Evaluation
压成一个万能入口，也不会让训练配置偷偷触发后续操作。

## 每一步先要能独立完成

仓库已经有不少可以复用的零件。`train` 会发布 checkpoint 和一份能由代码读取、之后不会被
悄悄改写的训练结果；`evaluate` 可以独立评估 checkpoint 或完整的预测结果，并发布正式结果。
生成图片时，外层运行代码已经负责读取配置和 checkpoint、核对输入与数量并完整写出文件；
具体任务只负责怎样生成这一批结果。公开的当前用法见
[工作流配置手册](../configuration/workflows.md)。

但这些零件还没有组成目标工作流。现有超分数据配置只说明仓库能把低分辨率输入和高分辨率
参考图组成训练数据，不等于已经有内置超分训练和图片放大操作。扩展也可以在训练中准备一个
不更新的教师模型，再由具体任务比较教师和学生的输出；这仍不等于已经有可发布的教师文件包
或内置蒸馏操作。

因此，只有对应的[蒸馏操作](consistency-distillation-support-plan.md)或
[超分操作](super-resolution-workflow-support-plan.md)已经可以单独运行，组合工作才有意义。
`ROADMAP.md` 还必须把本计划选为 `Next`，并明确第一条要交付的真实工作流。任务要有能在 CI
中快速完成的样例；每一步要有独立配置和明确结果；下游只能理解自己声明的输入类型。如果选择
蒸馏，具体蒸馏实现还必须愿意负责教师文件包的内容与兼容规则。

## 接通第一条流程需要补齐三层能力

第一层是让每个参与组合的操作有稳定的 Python 调用。训练、采样和 Evaluation 可以保留不同
参数和返回类型，但 CLI 只应负责解析参数和展示结果。相同配置从 CLI 或 Python 运行时，应选择
相同组件，并得到等价的核心结果、checkpoint 和结果清单。组合代码不能导入命令行内部辅助
函数，也不能另起命令行进程。当前内部的 `run_sampling()` 是否适合提升为稳定 library API，
要在实现时按公开调用边界重新判断，不能因为本计划已经提到它就视为承诺。

第二层是固定刚才描述的结果交接。教师文件包需要导出、读取、版本和兼容性检查；采样结果需要
精确样本数量和完整性证据；下游收到错误类型、缺失文件、摘要不一致或错误 raw/EMA 选择时，
必须在运行前给出能定位的错误。已有输出目录也不能被静默覆盖。

第三层才是一个短小的顺序调用。它按调用方写出的顺序执行，失败即停止，并在重用已有结果前
重新核对结果。首版不解释任意分支图，也不设计通用 `Pipeline` 基类。第一条流程稳定以后，再
用同样边界接通另一条。只有至少两条真实工作流反复需要相同的恢复和交接代码，才重新审查
[通用编排器计划](general-workflow-orchestrator-plan.md)；普通 Python 已经够用时，就不建立编排器。

## 什么结果才算真的接通

验收会从一个小型真实流程开始，而不是从抽象接口开始：

- 同一配置经 CLI 或 Python 调用时，组件选择、checkpoint、核心结果和结果清单等价；
- 被选中的完整流程能端到端运行，每一步也能拆开单独运行；
- 错误结果类型、缺失文件、摘要不一致、错误 raw/EMA 选择和重复输出目录都在计算前报错；
- 新任务可以由扩展加入，框架通用代码不按任务名称或具体类增加分支；
- 用户文档能清楚区分单次操作、显式顺序组合和以后才可能出现的通用编排器。

本计划不实现 consistency、超分辨率、latent 或 Stable Diffusion 算法，也不提供万能
`run(kind=...)`、任意 YAML 对象图、队列、缓存、并行分支、权限、集群调度、远程重试或可视化
流程编辑器。notebook 或服务长期复用的任务 Pipeline、可搬迁的推理文件包、自动任务识别和
模型中心下载仍作为更远的构想保留；它们要等真实需求出现后分别决定，不能随首版顺序调用
自动进入实现范围。

怎样发现和复制单次操作的配置模板也是另一个构想。它只帮助用户写出一次完整的训练、采样或
评估配置，不负责运行工作流，因此不会成为首条顺序流程的完成条件。候选名称、模板目录和发现
接口继续保存在附录中，等待自己的真实使用场景。

候选接口、任务专用 Pipeline、推理文件包、完整配置模板族、长测试矩阵和历史研究保存在
[维护者设计附录](notes/default-workflow-pipeline-support-plan/design-archive.md)。普通使用者不需要
阅读这份大型历史文件，附录中的名称也不代表当前接口。
